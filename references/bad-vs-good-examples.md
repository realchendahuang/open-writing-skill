# 什么样的文字算差，什么样的文字算好：真实正反例对照手册

很多人往写作 Skill 里塞样本时容易拿不准分寸：到底什么样的文字是必须枪毙的机器味废稿，什么样的文字才算值得放进 `voices/` 音色卡里让模型照着学的好人话？

下面这 4 组对照全部来自日常真实写作库：每一个 ❌ 差例子都是大模型默认吐出来被当场打回的废稿，每一个 ✅ 好例子都是改对味之后真正发出去的成稿。

## 二、 通识科普与深度长文：少背教科书定义，多拿日常小事打比方

**❌ 典型差例子（抄教材定义 + 结尾硬拔高）**
> 关于网络反向代理与端口映射的底层原理分析：
>
> 在现代分布式系统中，端口（Port）是传输层（TCP/UDP）服务访问点。网络通信中，IP 地址标识主机，端口号标识进程。反向代理（Reverse Proxy）充当服务器的前端，接收来自客户端的 HTTP 请求，并将其转发给后端服务。
>
> Nginx 是基于异步事件驱动模型的代表，而 Caddy 则采用了 Go 语言的并发模型并内置自动申请 SSL 证书机制。正确配置反代是微服务架构高可用的基石。

**✅ 改对味的好例子（从路由器背面贴纸切入 + 大楼接线员比喻）**
> 翻开家里无线路由器的背面，底部的贴纸上印着一行数字：192.168.1.1。你在浏览器里输入这串数字，就能打开路由器的管理后台。
>
> 但在很多人的印象里，网络通信一直是个黑盒：为什么不仅要有 IP 地址，后面还要挂一个像 :8080 这样的端口号？经常听程序员聊的反向代理、Nginx、Caddy，到底是在干什么？
>
> IP 地址相当于一栋大楼的门牌号。数据包只送到大楼门口是没用的，大楼里住着很多人，数据到底该交给谁？这时候就需要房间号，也就是端口。80 房间住着普通网页，443 房间住着加密网页，22 房间是管理员专用的后门，8080 房间可能是你刚写完的小玩具。
>
> 一台服务器对外通常只有一个公共 IP，如果你在机器上同时跑了博客、网盘和脚本，总不能让别人天天手敲端口号吧？这时候就需要在大楼门口放一个前台接线员，这就是反向代理。接线员守在门口，拆开信封看一眼收件人域名，找博客的悄悄转交到 3000 房间，找网盘的转交到 5244 房间。客人从头到尾只跟接线员打交道，根本不需要知道后院开了几个房间。

## 三、 互动提问探针：戒掉自问自答，把舞台留给别人

**❌ 典型差例子（好为人师，自己把一二三全答完了）**
> 我很好奇一个问题：大家在日常写代码时，AI 工具生成的代码质量参差不齐，容易产生所谓的架构腐化和代码屎山。
>
> 关于这个问题，底层的核心矛盾不是模型不够聪明，而是上下文缺乏全局约束。我最近摸索出了一套解法：第一是先写单元测试约束边界，第二是用规范的 prompt 限制生成范围，第三是多用小模块重构。
>
> 大家觉得这个思路对不对？你们团队是怎么解决屎山代码的？

>
> 大家平时是怎么用 AI 写代码的？
>
> 怎么能避免越写越屎山，最后维护不下去的问题？

## 四、 日常踩坑随笔：收起爹味说教，从自己踩坑平视聊起

**❌ 典型差例子（居高临下训人 + 危言耸听）**
> 很多新手开发者天天在网上吃二手法宝，动不动就跟着一些大 V 盲目崇拜复杂框架，这简直是自掘坟墓！
>
> 千万不要再去碰那些花哨的编排框架了！你们必须立刻停下来，回归纯原生开发！代码不是越多越好，而是越少越好。如果再不听劝，迟早会被技术浪潮彻底淘汰。

**✅ 改对味的好例子（拿自己以前走过的弯路开口 + 算清真实细账）**
> 写代码其实没必要天天盯着那些最贵的大模型。
>
> 我自己以前也总觉得必须上 Claude 最顶配的模型才能干活，后来动手做了一些批量处理的小工具，跑了一下账单，才发现有些活根本不需要杀鸡用牛刀。
>
> 日常写小脚本、补单元测试、改写前端样式，直接换成国产模型或者轻量的 Flash 模型，反应又快，成本连原来的十分之一都不到。
>
> 模型是干活的工具，不是供在神坛上的。适合具体场景、算得过来账的，才是好方案。
